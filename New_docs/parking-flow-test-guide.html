Web App flow guide

What changed, and how to test the full booking to checkout flow

This page is a local walkthrough for the current Web App changes in bookings, check-in, checkout, and payment simulation. It explains what the new flow does compared with the older behavior, then gives you an exact test plan you can follow step by step.

Short version

The app used to behave more like a basic booking-and-exit demo. It now behaves like a real parking operations flow with separate responsibilities for the driver and the operator.

Driver reserves a spot Operator approves entry Driver or operator closes the session Payment can be wallet, cash, bank, or phone

Big functional shifts

  • Reservations now carry a hold fee. A booking reserves a specific spot, deducts a reservation fee, and generates a reservation code.
  • Check-in is now explicit. The operator can check in a vehicle with a reservation code, plate number, or a walk-in flag.
  • QR check-in was added. The operator can generate a QR deep link, the driver confirms the plate, and the operator approves the request.
  • Checkout has multiple payment paths. The operator can close a session with cash or wallet deduction, and the driver can submit a manual bank or phone payment request.
  • Receipts are now generated at checkout. The session stores fare, tax, duration, payment method, and the final payment record.

Before

The flow was much flatter: booking, check-in, and checkout were not as tightly separated, and there was less visible state for approvals, spot assignment, and payment handling.

Now

The system tracks a real chain of state transitions across bookings, check-in requests, sessions, payment requests, and payments.

Why it matters

You can now test the app as a full operations flow instead of only verifying a page. The screens and backend data change together, which makes debugging much easier.

How to run it locally

Open a terminal in the Web App folder and start the front end plus the Firebase emulator path used by the app.

Terminal 1

npm run firebase:emulators

This starts the Functions emulator on port 5001. The app is already wired to use it in development.

Terminal 2

npm start

This starts the React app on http://localhost:3000.

Important: the current frontend automatically connects Functions to the local emulator in development, but it does not show a separate Firestore emulator hookup in the client bootstrap. For a fully isolated run, keep that in mind while testing.

Expected console message

Using Functions emulator at localhost:5001

Useful commands

firebase login, firebase use digital-parking-f9d2c

Role accounts

You will need at least one driver account and one operator account to test the end-to-end path.

Full flow: booking to check-in to checkout to payment

The best way to test the new behavior is to follow the flow below in order. Each step also notes what should change in the UI and backend.

1

Driver creates a booking

On the driver home screen, choose a parking lot, enter a plate number, and reserve a time window. The booking now creates a reservation code, assigns a specific spot, and charges the reservation hold fee.

Expected result: the driver sees a success toast, the spot is reserved, and the booking appears under active reservations with the generated reservation code.

2

Operator sees the reserved slot

The operator dashboard now shows reserved and occupied spots, along with a live lot status list. The spot assigned during booking should show as reserved instead of available.

Expected result: parking counters change, the reserved spot becomes visible, and the reservation code is shown in the operator view.

3

Driver check-in by QR or operator approval

The operator can generate a QR deep link. The driver opens the check-in confirmation page, enters the plate number, and submits the request. The operator then approves that check-in request from the pending queue.

Alternative manual route: the operator can use the manual check-in form and enter the reservation code or plate number directly. Walk-ins are also supported if the walk-in checkbox is enabled.

4

Session starts

Once the operator approves the check-in, a session is created. The booking status moves from reserved to checked in, the parking counters change, and the lot now has an active session for that plate.

Expected result: the operator sees the vehicle in the active sessions list, and the driver can see the active session from the driver dashboard.

5

Checkout begins

At exit time, the operator can search for the active vehicle by plate and choose a checkout method. The new flow supports cash, wallet deduction, or a manual payment request submitted by the driver first.

The checkout invoice now calculates duration, billed hours, base fare, tax, and final amount due before the session closes.

6

Payment is finalized

The system writes a payment record and closes the session. If wallet deduction is used, the driver balance is reduced automatically. If manual payment is used, the operator confirms the pending payment request before the session closes.

Expected result: the booking becomes completed, the session becomes completed, the payment record is created, and the exit gate is marked as unlocked in the UI feedback.

Scenario A: QR check-in

Driver flow
  1. Reserve a spot from Driver Home.
  2. On the operator dashboard, generate the driver QR.
  3. On the driver side, open the check-in confirm page using the QR link or token.
  4. Enter the plate number exactly as used in the booking.
  5. Submit the request and wait for operator approval.
Operator flow
  1. Open the pending QR check-in queue.
  2. Approve the request.
  3. Confirm that a session now exists and the booking changed to checked in.

Scenario B: Manual payment at exit

Driver flow
  1. Open Driver Home and find the active session.
  2. Choose manual bank or phone payment.
  3. Enter a reference code and submit the payment request.
  4. Wait for the operator to verify it.
Operator flow
  1. Open the pending manual payment queue.
  2. Review plate, amount, method, and reference code.
  3. Confirm or reject the transfer.
  4. Confirmation creates the payment record and completes checkout.

Operator direct checkout options

  • Cash: operator collects cash and closes the session directly.
  • Wallet: system verifies the driver's wallet balance and deducts the amount before closing the session.
  • Manual proof: driver submits a bank or phone transfer proof first, then operator confirms it from the queue.
If a driver has no registered driver profile, wallet checkout at exit should be disabled or fail with a balance or permission message. That is expected behavior.

What the new code writes

  • bookings holds reserved, checked in, completed, and expired booking state.
  • sessions tracks active and completed parking stays.
  • paymentRequests stores pending manual transfer proofs.
  • payments stores confirmed payment records and receipt data.
  • checkInRequests stores QR approval requests from the driver flow.
  • parkings counters are updated to reflect reserved, occupied, and available slots.
  • users wallet balances are reduced for reservation fees and wallet-based checkout.

Recommended test script

  1. Log in as a driver.
  2. Reserve a space for a future time window and note the reservation code.
  3. Log in as an operator and confirm the spot is reserved.
  4. Generate a QR and complete the driver QR check-in, then approve it as operator.
  5. Check that the session becomes active.
  6. Test driver wallet checkout or operator direct checkout.
  7. Repeat with a manual bank or phone payment request and confirm it from the operator queue.
  8. Optionally trigger the expire-bookings cron and verify no-show bookings are cleared.

What to verify in the UI

  • Reservation code is shown after booking.
  • Reserved spot appears in the lot map.
  • Driver QR confirm page accepts a plate and shows pending approval.
  • Operator can approve or reject check-in requests.
  • Checkout shows fare, tax, and total amount due.
  • Manual payment queue shows the reference code and amount.
  • Receipt modal appears after wallet checkout or confirmed checkout.

Troubleshooting and gotchas

1. Booking fails with no available slots
The parking lot is out of capacity for the chosen time window. Try another lot or a different time range.
2. Booking fails with insufficient wallet balance
The driver wallet must cover the reservation hold fee. Top up the wallet and try again.
3. QR check-in says token expired
Refresh the QR on the operator dashboard and scan the new one. The token is short-lived by design.
4. Wallet checkout fails
The driver's wallet balance may be too low, or the vehicle may be a walk-in without a registered driver profile.
5. Manual payment never appears in the operator queue
Check that the driver submitted the payment from the active session, with the right plate number and parking lot.
If the app is still pointed at a live project, be careful with test data. For real local-only validation, make sure your Firebase setup is fully isolated before running destructive scenarios.
